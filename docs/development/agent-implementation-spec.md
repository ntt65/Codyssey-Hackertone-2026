아래 본문은 원본 명세를 보존한다. 대상 실행부는 `backend/agent_v3.py`로 분리했고 기존 `naito_chat.py`에는 v3 분기 3줄만 추가했다. 프론트 세션 전송은 신규 `frontend/js/agent-session.js`와 기존 JS 접점이다. 원본 전체 history/내비게이션 엔진을 복사하지 않았다.

대상 검증은 backend 241/241·HTTP/store/DOM 23/23·legacy 상태 15/15·도구26 PASS다. 아래 §11 원본 파일맵·§12의253/19/9·§13 원본 실모델 사용량과 합산하지 않는다. 대상의 제품 diff/음성3결함 보완/기존 docstring7 FAIL/실기기 미실시는 [실행 체크리스트](agent-engine-port-progress.md)와 [게시 결과](agent-engine-publication.md)를 따른다. 기준 develop은 e5697e2, 검증 이식코드는 e7163aa, 문서 게시기록은 ed923aa다.

## 1. 제품 목표와 사용자 요구

목표는 사용자가 검색 조건을 채우는 수고를 줄이고, **편하게 이야기하는 동안 니즈를 파악해 실제 콘텐츠를 제안하고 반응에 따라 좁혀 가는 에이전트**다. 목적·취향·상황을 기억하고 새 발화가 바꾸는 부분만 갱신한다. 날짜·종료시각·세부 장르가 없다는 이유로 대화를 필수 입력 폼처럼 멈추지 않는다.

출발점은 사용자가 먼저 제안한 **“전체 대화 맥락을 유지하고 그중에서 서비스 메뉴를 설정하며, 없는 선택 조건은 필터에서 제외하자”**는 방향이다. 후속 대화에서는 이를 **대화 맥락·추천 설정·메뉴 진행**의 세 축으로 명확히 정리했다. 연구와 KONNECT 검토는 이 사용자 요구를 구현할 방법을 고르는 참고였으며, 이 아이디어의 출처를 기존 프레임워크나 에이전트의 독자 제안으로 바꾸지 않는다.

사용자 피드백은 다음처럼 실제 구현 판단에 반영했다.

- “잔잔한 음악”은 이미 말한 공연 목적에 붙는 분위기 선호다. 임의로 클래식·국악 장르로 확정하거나 잘못된 메뉴 키 하나 때문에 전체 응답을 폐기하지 않는다.
- “무슨 조건?”은 질문의 뜻을 설명해 달라는 요청이다. 목적을 잊고 활동부터 다시 묻지 않는다.
- “3번”은 현재 보이는 콘텐츠의 선택이다. 공연/전시 목적이나 출발지를 새로 정하는 입력이 아니다.
- 산책 추천에는 실제 주 목적지가 필요하다. 공원 이름이 포함된 화장실·주차장을 가까운 실제 장소라는 이유만으로 추천하지 않는다.
- 후보를 더 보고 상세·지도·저장을 오가더라도 같은 대화·조건·읽던 위치를 유지한다.

모든 활동 의도를 대화로 받는 것과 모든 활동의 실시간 데이터를 보유한 것은 구분한다. 가능한 정보를 먼저 제공하되 없는 작품·회차·영업·예약 정보를 만들어 결과를 채우지 않는다.

## 2. 핵심 세 축과 실제 사실의 분리

| 축 | 현재 상태/계약 | 의미와 불변 조건 |
|---|---|---|
| 대화 맥락 | `understanding`, 의미 `history`, `active_question` | 원하는 목적·활동·분위기·선호/제외, 현재 질문의 뜻과 답변 대상. 설명·불만·짧은 단답을 앞 대화와 연결 |
| 추천 설정 | `conditions`, `field_meta`, `hypotheses`, `pending_changes` | 출발지·선택 날짜/시간·무료/예산·명시 제외·필수 제약과 확인 상태. 말하지 않은 값을 오늘·false·임의 좌표로 채우지 않음 |
| 메뉴 진행 | `display_batch`, `display_history`, `selected_content`, `next_action` | 현재 보이는 카드 순서, 어떤 콘텐츠를 골랐는지, 다음에 무엇을 할지. 선택만으로 앞 두 축을 초기화하지 않음 |
| 공통 사실 근거 | `tool_facts`, `result_context`, 후보 snapshot | 실제 공급자 ID·제목·좌표·기간·가격·출처·조회 시각과 실행 조건. 세 축에서 참조하지만 LLM의 설명으로 사실을 대체하지 않음 |

예를 들어 전시 후보를 본 사용자가 “3번”이라고 말하면 현재 표시 묶음의 세 번째 ID만 선택한다. 기존 전시 목적·출발지·무료 조건·대화 history의 앞부분은 그대로 보존한다. 다음 말이 잡담이나 불명확한 표현이어도 선택과 목적을 유지하며 현재 할 수 있는 행동을 안내한다.

관련 조건이 실제로 바뀌면 이전 결과·선택 권한을 무효화한다. 취소된 선호를 전체 원문에서 다시 추출해 되살리지 않으며, 서비스 전환 시에는 그 서비스에 종속된 분류·선호·보류·후보를 정리하고 공통 위치·날짜처럼 유지할 수 있는 정보는 남긴다.

## 3. 대표 사용자 흐름

### 전시 탐색 → 세 번째 선택 → 상세·지도·저장

1. 사용자가 전시를 보고 싶다고 말한다. 확인된 지역이 없으면 지역처럼 실제 조회를 바꾸는 정보 한 가지를 묻는다. 날짜 미정이라는 이유만으로 탐색을 막지 않는다.
2. 실제 문화 콘텐츠를 조회하고 명시한 필수 조건을 적용한다. 검증 가능한 원문 근거가 있으면 취향 정렬에 사용한다.
3. 서버가 발급한 현재 표시 묶음의 순서대로 최대 세 개를 보여준다. 무작위 추출이 아니다.
4. 카드의 `이곳 선택`, 상세의 같은 버튼, “3번/세 번째”가 동일한 서버 선택 계약으로 이어진다. 단순 상세 열람은 선택으로 간주하지 않는다.
5. 성공한 선택은 같은 콘텐츠의 상세로 연결한다. 선택 자체에 모델·공급자 재조회가 추가되지 않고 날짜 필수 질문도 생기지 않는다. 지도와 저장도 같은 후보 ID와 snapshot을 사용한다.
6. 다른 후보 요청으로 두 번째 묶음을 보고 있다면 “3번”은 그 묶음의 세 번째다. 전체 서버 풀의 세 번째나 과거 말풍선의 세 번째로 추정하지 않는다.

현재 선택은 **임시 관람 대상 지정**이다. 예매·입장 가능·방문 일정 확정이나 새 찜 기능을 뜻하지 않는다. 기존 `내 나들이에 저장`은 별도 브라우저 보관 행동으로 유지한다.

### 산책 → 실제 목적지 분류 → 적합한 수만 반환

산책은 현재 출발 좌표로 `공원`을 검색한다. 기존 거리순 첫 다섯 건 안에서 공급자 상세분류와 그룹을 확인해 화장실·주차장·관리소 등 부대시설, 다른 용도, 산책 목적지가 확인되지 않는 후보를 먼저 제외한다. 그 뒤 기존 필수 조건과 순위를 적용한다.

정상 공원이 두 개면 두 개만, 한 개면 한 개만 보여준다. 모두 부대시설/미확인이면 조회 범위의 0건을 안내한다. 이름·ID·좌표를 부모 공원으로 바꾸거나 결과 개수를 채우지 않는다. 정상 공원 이름에 ‘화장실’ 안내가 있다는 이유만으로 제외하지도 않는다.

이는 “조회한 첫 다섯 건에서 적합 후보를 확인하지 못함”이며 “근처에 공원이 없음”이라는 판정이 아니다. 이번 범위에서는 추가 페이지·반경 확대를 하지 않았다.

### 질문 설명·오류 뒤에도 같은 목적 유지

공연 목적을 말한 뒤 “무슨 조건?”이라고 물으면 현재 질문의 뜻을 설명한다. 이어 “잔잔한 음악”이라고 답해도 유효한 분위기는 수집한다. 지역 질문에 대한 답이 아니라는 이유만으로 취향을 버리거나 모든 조건을 다시 요구하지 않는다. STT 실패 공지는 현재 질문을 덮어쓰지 않는다. 도구 장애가 생기면 이해한 의미는 보존하고 실패한 조회만 명시적으로 재시도할 수 있다.

## 4. 실제 제공 능력과 방문 가능성의 경계

| 범위 | 현재 확인해 제공하는 것 | 보장하지 않는 것 |
|---|---|---|
| 공연·전시 등 공개 문화 콘텐츠 | 기존 문화 공급자에서 확인한 실제 행사 ID·제목·기간·원문 시간·공개 요금·좌표·출처 | 모든 문화 콘텐츠의 완전한 목록, 날짜별 회차·좌석·예약 완료 |
| 영화 | 기존 지도 공급자의 실제 영화관 위치·직선거리 | 영화 작품·상영시간표·상영 회차·예매·코미디 취향에 맞는 작품 조회 |
| 산책·카페·식사 등 일반 장소 | 기존 장소 검색의 확인된 위치·주소·분류와 조회 범위 | 현재 영업·입장·예약 가능, 직선거리로 추정한 도보시간 |
| 방문계획 검토 | 사용자가 명시한 날짜·시각·출발지와 최소60분 검증, 같은 서비스/필수조건/취향을 유지한 자료 확인 | 실제 이동 완료, 공연 종료시각·운영 예외·예약까지 검증됐다는 포괄 보장 |

행사 기간 안에 있다는 사실과 그 날짜에 운영/입장 가능한지는 다르다. `PRO_TIME` 같은 원문 운영 안내가 있다고 날짜별 회차표가 생긴 것은 아니다. 가격·운영·예약 근거가 없으면 미확인으로 남긴다. 기간·운영시간·회차·예약은 서로 겹칠 수 있는 속성이며 업종 하나로 모두 결정하지 않는다.

콘텐츠 탐색은 `content_exploration` 또는 `venue_exploration`, 방문 검토는 `visit_plan`으로 구분한다. 후보에는 `visit_status`와 `visit_validation_context`를 둔다. 현재 방문 경로도 확인되지 않은 예약·운영·이동을 `verified`로 승격하지 않고 `unknown`으로 표시한다. 날짜 없는 탐색을 위해 기존 방문계획의 60분 규칙을 제거한 것은 아니다.

## 5. 서버·모델·도구·UI의 역할

흐름은 **사용자 이벤트 → 대화 예약 → 의미 해석/부분 통합 → 정책 선택 → 필요한 실제 조회 → 적합성/필수조건 검사 → 선택적 의미 정렬 → 원자 commit → 화면 표시**다. 카드 선택·명확한 번호처럼 기존 상태로 처리 가능한 동작은 모델 이전에 해결한다.

- **모델:** 자연어 의도·의역·질문에 대한 답·선호·정정·설명 요청을 `acts/updates`의 의미 후보로 제안한다. 후처리 정렬에서는 실제 후보 원문의 관련성만 판단한다.
- **의미 모듈:** 현재 발화의 근거·타입·대상 ID를 항목별로 확인해 `add/remove/replace`한다. 한 후보의 오류가 유효한 목적·취향을 함께 폐기하지 않게 한다. 원문 인용은 실제 발화에 있어야 하지만 정규화 의미가 원문과 같은 문자열일 필요는 없다.
- **정책:** 현재 질문·기존 정보·실행 필요성·반복 부담으로 설명/질문/조회/선택/복구 중 행동을 결정한다. 단어 목록으로 모델의 모든 의역을 다시 거부하는 구조를 피한다.
- **도구/코드:** 실제 장소·좌표·기간·시간·가격·ID·출처와 필수 조건을 판정한다. 실제0건과 연결 장애를 구분한다. 관련 조건의 변경과 실행 키가 다른 pool 재사용을 차단한다.
- **UI:** 서버 canonical 상태와 발급된 표시 묶음을 기존 말풍선·카드·상세에 표시하고 이벤트를 보낸다. 서버가 실패한 조작을 별도 로컬 조건 변경으로 성공 처리하지 않는다.

연구에서는 정보상태/현재 질문과 task/discourse 분리, 부분 이해·복구, 질문 비용, 전체 대화의 과업 달성과 수정 비용을 참고했다. CLIPS·TRINDI·RavenClaw·PARADISE를 설치하거나 수식·강화학습 루프를 가져온 것은 아니다. 채택 범위와 원문 읽은 구간은 [v3 설계](https://github.com/Lab678-Hackathon/lab678/blob/dj/agent/docs/development/agent-redesign-v3.md)에 있다. 문헌이 현재 한국어 LLM 품질을 보장한다고 주장하지 않는다.

## 6. API와 상태 계약

`/preview/chat`의 기존 계약을 유지하면서 `agent_version=3`으로 새 경로를 구분한다. 현재 프론트 기본 경로는 v3이고 `?agent=legacy`로 기존 계약 회귀를 실행할 수 있다. v3 실패를 예전 API나 로컬 파서의 성공으로 조용히 바꾸지 않는다.

```json
{
  "agent_version": 3,
  "conversation_id": "server-issued-handle",
  "epoch": "server-issued-epoch",
  "document_id": "per-document-id",
  "lease_generation": 1,
  "turn_id": "unique-turn-id",
  "turn_seq": 1,
  "expected_revision": 0,
  "event": { "type": "message", "text": "전시를 보고 싶어요" }
}
```

위 값은 구조 설명용이다. 실제 handle/epoch/revision/후보 ID는 서버 응답을 사용한다. 키·실제 환경 파일·사용자 정밀 위치는 이 이슈나 일반 오류 로그에 넣지 않는다.

| 이벤트 | 역할 |
|---|---|
| `open`, `heartbeat`, `release` | 대화 생성/재연결과 writer lease 관리. 모델 호출 없음 |
| `message` | 새 사용자 발화. 명확한 콘텐츠 번호/유일한 이름은 현재 표시 묶음에서 먼저 처리 |
| `select_origin`, `set_current_location` | 실제 장소 후보나 사용자 기기 위치 선택. 확인된 기존 값 변경은 동의 경계 유지 |
| `confirm_change`, `dismiss_change` | 해당 pending 변경만 수락/거절 |
| `proceed` | 현재 단계 진행. 명시한 방문계획 mode만 방문 검증으로 전환 |
| `select_content` | 후보 ID·결과 실행 키·표시 batch ID로 이번 임시 대상 선택 |
| `retry_tool` | 실패 action ID와 현재 조건을 대조해 해당 도구만 재실행 |
| `restore` | 압축한 이전 사용자 주장을 검증해 새 상태에 복원. tool facts/verified 수입 금지 |

응답은 `state`, `conversation`, `assistant_text`, `next_action`, `tool_result`, 안전한 `diagnostics`를 중심으로 한다. 일반/기존 요청은8192바이트, v3 복원만32768바이트의 별도 상한을 적용한다. 긴 원문 전체를 매 턴 다시 보내지 않고 서버 상태와 개별 이벤트를 사용한다.

HTTP400은 입력, 409는 revision/lease/동일 대화 예약 경합 등 동기화, 429는 전역 동시 처리/제공자 제한, 502는 제공자 연결·형식, 503은 미설정, 504는 시간초과, 내부 불변식 문제는500으로 구분한다. 도구가 정상 처리돼 구조화된 `source_error`를 전달하는 경우에는 응답 HTTP200과 함께 그 도구 상태를 읽어야 한다. 의미 성공·실제0건·source 장애를 같은 상태로 집계하지 않는다. 캐시된 오류도 원래 HTTP 상태를 유지한다.

## 7. 표시 묶음과 콘텐츠 선택

서버 전체 pool과 현재 표시 묶음을 분리한다.

```json
{
  "display_batch": {
    "id": "server-issued-batch-id",
    "execution_key": "verified-result-key",
    "candidate_ids": ["source:example-1", "source:example-2", "source:example-3"]
  }
}
```

`state`와 `tool_result`에 같은 묶음을 제공하고, 프론트는 그 ID 순서대로 최대 세 개만 렌더한다. 프론트가 다시 다른 세 개를 고르거나 전체 pool의 번호를 붙이지 않는다. batch ID의 임의 발급은 식별자 생성이며 후보를 무작위로 고른다는 뜻이 아니다.

`select_content`는 `candidate_id`, `result_execution_key`, `display_batch_id`를 전달한다. 서버는 현재 대화의 실행 키·표시 순서·실제 tool 후보·조건·필수 보류를 대조하고 검증된 후보 snapshot을 `selected_content`로 저장한다. 성공한 `next_action.type=content_selected`의 `candidate`와 canonical 선택 ID가 같아야 상세로 이동한다. 단순 상세 열람용 `selectedCandidate`는 이 서버 선택과 구분한다.

명확한 번호/유일한 후보명은 모델 호출 이전에 같은 선택 이벤트로 해석한다. “3번 말고 무료만” 같은 복합 조건을 번호 선택으로 가로채지 않는다. 오래된 batch·다른 대화·변경된 날짜/좌표/무료·예산·제외 조건의 선택은 현재 상태를 보존하는 안내로 거절하고 모델/source를 새로 실행하지 않는다. 화면의 오래된 카드는 선택 불가로 표시하고 별도 HTTP 검증도 유지한다.

명확한 “다른 곳도 보여줘”는 동일 실행 키의 확인된 pool에서 다음 묶음을 발급한다. 일반 잡담·불명확한 말·단순 진행마다 재검색하지 않는다. 현재 범위의 후보를 다 보여줬으면 그 사실을 알리고 임의로 과거 후보를 새 후보처럼 채우지 않는다.

정렬은 실제 조건을 적용한 후보에 관심어·검증된 원문 관련성·직선거리 등을 사용한다. 취향/관심어가 없으면 거리와 안정적인 ID 순서가 기본이며, 명시적인 ‘더 가까운 곳’은 유효한 후보 집합에서 거리 우선으로 처리한다. 도보시간을 직선거리로 보장하지 않는다.

## 8. 상태 권위·격리·중복·복원

`ConversationStore`는 표준 라이브러리 기반 단일 프로세스 메모리 저장소다. 사용자 비활동30분 TTL, 최대100대화, 최근20응답 캐시와 해당 epoch의 `last_committed_seq` watermark를 둔다. heartbeat만으로 비활동 TTL을 무한 연장하지 않는다. 포화 시 활성 상태를 몰래 버리지 않는다.

매 문서 실행마다 메모리에서 새 `document_id`를 만들고 writer lease10초/heartbeat5초와 연결한다. 활성 owner가 있는 복제 탭은 새 대화로 분기한다. 새로고침은 release 또는 lease 만료 뒤 같은 대화에 재연결한다. 해제가 실패한 경우 즉시 소유권을 빼앗지 않으며 인계 대기가 생길 수 있다.

짧은 lock 안에서 턴을 예약하고 모델·지도·문화 조회는 lock 밖에서 실행한다. 최종 commit은 예약 token·epoch·revision·document·lease generation을 모두 대조한다. lease 인계·새 대화·TTL 만료 뒤 옛 worker가 도착해도 현재 상태를 만들거나 덮지 못한다.

동일 요청 재전송은 진행 중 상태 또는 캐시 결과를 반환한다. 캐시 밖 과거 seq는 상태 재동기화만 하고 모델/도구를 다시 실행하지 않는다. 유효 의미와 도구 결과 또는 `source_error`를 한 번 함께 commit한다. 도구 실패가 유효한 목적·취향을 롤백하지 않는다. `retry_tool`은 새 턴으로 실패 도구만 재시도하고 이미 반영한 의미를 다시 적용하지 않는다.

서버 재시작/만료 뒤 복원하는 내용은 목표·선호·명시 조건·미해결 hard·현재 질문과 그 근거 등 허용 항목이다. 복원값은 사용자 주장으로 취급하고 원래의 confirmed/verified/revision/도구 cache를 권위로 수입하지 않는다. 위치는 지명으로 재조회하며 확인할 수 없는 필수 조건은 삭제하지 않고 미해결로 유지한다. 선택 후보도 미검증 사실로 부활시키지 않는다.

브라우저의 익명 visitor ID는 저장 namespace이지 실제 사람 인증이 아니다. 대화는 visitor/대화별 sessionStorage, 기존 저장 장소는 visitor별 localStorage 범위로 분리한다. 구형 고정 키의 자료는 자동 병합하거나 삭제하지 않는다. 다중 worker/다중 서버·서버 재시작을 넘는 exactly-once·인증 권한까지 구현한 것은 아니다.

## 9. UI와 이전/홈 동작

기존 말풍선·입력·카드·출발지 팝업·상세·지도·내 나들이를 유지했다. v3 본체에서는 최소 JS 계약을 연결했고, 이후 승인된 이전/홈 개선에서만 기존 header 버튼과 최소 CSS 정렬을 보완했다. 선택 단계는 기존 카드/상세 영역에 JS로 `이곳 선택`을 추가했으며 새 페이지·피드·표·달력·외형 재설계를 하지 않았다.

- 대화→상세→지도는 같은 상세와 같은 대화의 읽던 위치로 돌아온다.
- 내 나들이나 홈 미리보기에서 들어온 상세는 그 진입 출처로 돌아간다.
- 지도 확대 상태의 첫 이전은 확대 해제, 다음 이전은 상세 복귀다.
- 내부 이력이 없는 직접 URL은 안전한 앱 내부 부모/홈으로 복귀한다. 외부 history 길이만 보고 앱 밖으로 보내지 않는다.
- native back/forward와 앱 이전을 앱 소유 route entry로 연결하고 fallback은 replace로 처리해 왕복 고리를 피한다.
- 복귀 snapshot은 스크롤·포커스·카드/진입 맥락만 복원한다. 서버 목적·조건·대화 ID를 과거 값으로 되돌리지 않는다.

복귀 시 새 인사·새 대화·미전송 입력 초기화·강제 맨끝 스크롤·STT/TTS 자동 시작을 하지 않는다. 선택 직후 숨겨진 채팅의 finally/render나 예약된 음성 callback도 상세 화면을 덮거나 녹음을 다시 시작하지 않게 했다.

## 10. 문제 → 확인한 원인 → 최종 수정

아래의 ‘확인’은 소스/경계/실제 통합 재현 근거가 있다는 뜻이다. 사용자 과거 실패의 단일 직접 원인을 모두 소급 확정한 것은 아니다.

| 문제 | 확인한 원인 또는 관측 한계 | 최종 처리 |
|---|---|---|
| 정상 목적도 조건 추출 실패로 끝남 | 의미가 조건 JSON/grounding 전체 성공 뒤에만 진행되던 구조 | 의미·조건 후보를 부분 검증하고 유효 정보 보존 |
| 공연 목적에 변경 조건부터 요구 | 모델의 잘못된 분류 후보·오래된 보류가 현재 목적보다 우선 | 보류의 근거/범위 구분, 실제 변경 의도·확정값 충돌만 확인 |
| 잔잔함을 장르로 확정하거나 전체502 | 분위기와 category 혼용, 허용 밖 후보가 응답 전체를 막는 경계 재현 | 의미 차원 분리, 잘못된 category/mood만 격리 |
| 질문 뜻을 물어도 같은 질문 반복 | 설명 대화행위/현재 질문 연결 부족 | active_question과 explain_question, 앞 목적 유지 |
| STT 공지가 단답 해석을 바꿈 | 상태 안내가 일반 assistant history에 포함 | 상태 이벤트와 의미 이력 분리 |
| 장소를 계속 다시 입력·선택하게 함 | 단답 grounding과 실제 지도 채택 경계 | 현재 질문 대상을 사용, 실검색 유일 정확일치 채택, 모호한 실제 후보만 선택 |
| 새 출발지 조회가 변경 동의를 우회 | 조회 후보 때문에 기존 확정 좌표를 먼저 지움 | 실제 새 후보와 기존값 비교, 동의 전 기존 좌표 유지 |
| 오류 재전달이 성공으로 바뀜 | 캐시 분기에서 원502도200으로 반환 | 원 HTTP 상태를 commit/재전달에 보존 |
| 방문 전환이 없거나 다른 분류가 섞임 | mode 누락, 전체 분류 기반 별도 추천이 목적/취향을 잃음 | 명시 visit 전환,60분 검증 뒤 같은 explore 서비스/필터/취향 사용 |
| 상세가 과거 날짜·출발지를 빌려 씀 | 전역 lastRequest 참조 | 후보별 result/origin/visit context와 snapshot 사용 |
| 산책에 화장실·주차장 추천 | 분류는 보존됐지만 주 목적지 적합성 검사 없음 | 상세분류·부대시설 역할 판정→기존 hard→순위 |
| 전시 ‘3번’이 선택 대신 재조회 | 표시 묶음과 선택 계약 부재, 프론트 표시와 전체 pool의 혼동 | 서버 display_batch와 동일 select_content, 번호 pre-model 처리 |
| 잡담·빈 의미 뒤 활동부터 재질문 | 현재 목적/후보보다 일반 chitchat 질문을 먼저 선택 | 현재 단계 안내와 목적 보존. 정확히 정상 빈 의미 envelope만 제한적 회복 |
| 새 정상 카드도 stale로 거절 | 실제 지도 원점은 주소 포함, 탐색 context는 label/좌표만 있어 raw dict 비교 불일치 | 동일한 출발지 의미값으로 비교. 주소 표시 차이만 허용, 좌표/날짜/요금/제외 변경 차단 |

과거 공연 “잔잔한 음악” 직후 사용자가 본502의 단일 직접 원인은 당시 전체 상태/원문 응답이 없어 **미확정**이다. 잘못된 메뉴 후보 등 유사 경계는 재현·수정했고 별도 실제 모델 검증을 수행했지만 이를 당시502의 확정 증거로 바꾸지 않는다. 산책 화장실의 당시 실제 카카오 분류와 전시 번호 실패 당시 모델 출력·STT도 확보하지 못했다. 그 대신 해당 결함이 발생할 수 있는 경로를 합성/실제 HTTP 경계로 입증하고 회귀로 고정했다.

## 14. 재검증 방법

코드·필요한 개발 의존성·테스트용 브라우저가 준비된 환경에서 다음을 실행한다. 실제 환경 파일을 출력하거나 다른 사람의 키를 복사할 필요가 없는 고정 경계 검사다.

```text
python -X utf8 -m unittest discover -s backend -p "test_*.py" -q
node utils/scripts/check_agent_v3.cjs
node utils/scripts/check_navigation.cjs
node utils/scripts/check_dialogue_flow.cjs
node utils/scripts/check_agent_regressions.cjs
node utils/scripts/check_agent_http.cjs
python utils/scripts/harness.py --tests
```

브라우저 스크립트는 설치 환경에 맞는 `PLAYWRIGHT_MODULE`과 필요 시 `CHROMIUM_PATH`, Python 경로를 환경변수로 지정한다. 사용자별 절대 경로나 실제 키를 소스에 넣지 않는다. QA 스크립트가 만든 임시 loopback 서버/브라우저만 시작·종료하며 기존 개발 서버를 갈아끼우지 않는다. 외부 네트워크·장치는 차단/모의한다. 하네스의 기존 docstring7개 실패는 위 알려진 상태와 대조한다.

로컬 사용 시험은 `http://127.0.0.1:5173/`에서 Ctrl+F5 후 새 대화를 시작해 새로 조회한 카드로 한다. 과거/복원된 미검증 snapshot에 최신 선택 권한을 붙이지 않으므로 이전 카드는 열람만 가능할 수 있다. 다른 팀원의 PC에는 자신의 서버/API origin·허용 origin·환경 설정이 필요하며 로컬 주소 자체가 배포 URL은 아니다.

실제 사용자 시험에서는 전시/공연 목적→지역→취향→현재3번, 다른 곳→새 묶음3번, 상세/지도/이전, 필수 조건 정정, 불명확한 말 뒤 현재 목적 유지를 확인한다. 실제 기기 실패는 해당 turn/revision·단계·상태를 안전하게 기록하고 원문·정밀 위치·키를 공개 로그에 넣지 않는다. 단편 문장200만으로 전체 흐름 성공을 선언하지 않는다.

## 15. 남은 제한과 후속 제안

- 일반 한국어/자유 대화 성공률과 사용자 만족도를 충분한 표본으로 입증하지 않았다. 작은 두 번 반복·모의 PASS를 전체 품질 보장으로 확대하지 않는다.
- 산책 지원 상세분류는 보수적인 제품 정책이지 카카오 전체 분류표가 아니다. 실제 정상 장소도 미지원/결측 분류이면 제외될 수 있다. 다른 업종의 부대시설 공통 적합성 확대와 추가 조회/반경 정책은 별도 검토다.
- 영화 작품·상영표·예매, 날짜별 확정 회차·좌석, 잔여 토큰/쿼터 조회는 연동했다고 주장하지 않는다. 새 공급자·모델·키 변경은 이번 범위가 아니다.
- 날짜 미정 콘텐츠 탐색과 PRD F03/F07/H11·S02/S03의 방문 근거 정책 차이, 임시 선택 F08/F10/H18 등은 Product/UX 팀 검토 사항이다. 개인 구현 허락을 팀 전체 기획 승인으로 바꾸지 않았고 정본을 임의 개정하지 않았다.
- 단일 프로세스·임시 저장의 한계, 인증 부재, 재시작 이후 중복 보장 제한은 유지한다. 브라우저별 사용자 구분과 실제 사람 인증을 혼동하지 않는다.
- 새 ♡찜 UX, 선택한 행사에 고정된 관람 날짜·가용시간·회차 UI, 선택/방문 검증 상태의 시각 구분, **한 단계 되돌리기**는 후속 제안이다. 화면의 ‘이전’은 대화 조건 변경 취소와 다르며 현재 그 기능을 대신하지 않는다.

KONNECT의 원본도 다시 읽고 다음 두 가지를 후속으로 권장했다. 아직 추가 구현한 기능이 아니다.

1. `reasons.py`·`timing.py`에서 검증된 이유와 가능/불가/미확인 구분을 참고해, 선택한 후보에 **근거 있는 이유1~2개와 남은 확인 하나**를 연결하는 설명을 개선한다. 현재 원문 근거·사실 필드는 있으므로 그것을 재개발하는 제안은 아니다.
2. `exclusion.py`에서 적용/제외/안내를 구분하는 아이디어를 참고해 **0건 원인별 대안**을 제시한다. 현재 `excluded_counts/not_applied`를 활용하되 원본의 조건 자동 해제는 채택하지 않는다. 필수 조건 완화는 사용자 선택이 필요하다.

KONNECT를 통째로 이식하거나 Supabase·로그인·다중 LLM 루프를 필수로 추가하지 않았다. 사용자 정정 우선·tool 사실 보존·부분 실패 구분은 현재 v3에 이미 반영된 사항이며 같은 기능을 미래 계획으로 중복 제안하지 않는다.

## 16. 팀 검토와 복구

개발 검토는 backend 의미/조건/도구의 역할, 현재 batch와 선택 검증, 데이터 결측·오류 상태, writer/CAS·재전송을 우선 확인하면 된다. Product 정민규·UX/팀장 손희영에게는 날짜 없는 탐색/임시 선택 정책, 기존 화면 안의 선택과 이전 동작, 방문 가능성 오인 여부를 검토 요청할 항목으로 남긴다. 역할 수락·최종 승인·실기기 QA 완료로 기록하지 않는다.

변경 전 소스와 patch·단계별 hash 검증 보존본이 있다. v3 본체, 산책/이전, 선택 연결을 작업 단위로 비교해 필요한 부분만 되돌릴 수 있게 구분했다. 복구는 해당 단계/파일의 차이를 먼저 확인하고 기존 출발지 패치·다른 단계 개선·사용자 대화/저장·개인 자료를 보존하는 방식으로 진행한다. 전체 폴더 삭제나 일괄 reset으로 되돌리는 방식을 전제로 하지 않는다.

v3를 중지해야 한다면 명시된 compatibility 경로와 이전 계약을 사용하고, 미검증 새 namespace 자료를 과거 상태에 자동 병합하지 않는다. 서버 재시작 시 메모리 대화가 사라질 수 있다는 점과 새 epoch/복원 절차를 함께 확인한다. 이번 원격 공개의 대상은 `dj/agent`이며 `main`/`develop` 병합·실서비스 배포·사용자 데이터 삭제는 포함하지 않는다.

이 이슈의 완료 근거는 위 구현과 재현 가능한 검증 결과다. 미실시·미확정·후속 항목도 같은 본문에 남겨, 다음 담당자가 PASS 숫자만 보고 실사용 품질이나 지원 범위를 과대 해석하지 않도록 한다.
