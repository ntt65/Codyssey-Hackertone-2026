# develop 원형에 에이전트 엔진을 선택 이식하는 계획

2026-11-01 · 소스 `dj/agent` → 대상 새 `dj/develop` · **이식·검증 후 사용자 요청으로 검증 코드 e7163aa push 및 PR69 발행 완료.** 소스 성적과 대상 성적을 구분하며 develop 병합·배포하지 않았다.

> 후속 게시 승인 “이대로 푸시 … PR발행해”에 따라 이전 원격 tip을 보존한 뒤 기대 SHA lease로 게시했다. 앞선 로컬 미게시/새 PR 미승인 문구는 당시 계획 이력이며, 최신 결과는 [게시 기록](agent-engine-publication.md)과 [PR69](https://github.com/Lab678-Hackathon/lab678/pull/69)를 따른다.

원본의 상세 설계·의도·실패/검증 근거는 [에이전트 개발 명세](agent-implementation-spec.md)를 따른다. 이 문서는 현행 소스 전체를 새 기준에 복사하는 지시가 아니다.

단계별 실제 실행/점검/보완은 [실행 체크리스트](agent-engine-port-progress.md)를 함께 갱신한다. 소스 보존본에는 이식 착수 당시의 승인 계획이 남고, 대상 문서에는 실제 결과가 추가된다.

## 1. 사용자 결정과 목표

사용자는 `dj/agent`가 팀의 develop에서 크게 바뀐 점을 우려해 **“develop branch를 그대로 이어 받은 dj/develop에 지금 우리가 개선한 agent를 반영”**, **“dj/agent에 개발상세 … dj/develop에 이전할 계획도 자세히 … 각각 저장 … 일단 계획세워”**라고 요청했다. 조사 후에는 **“그냥 develop을 깨끗히 카피해서 엔진을 이식 … 이전 dj/develop은 신경쓰지마”**라고 기준을 정했다.

따라서 **최신 원격 develop의 파일 구성을 그대로 출발점으로 삼고, 개선 엔진·필수 연결부·선택 동작만 옮긴다.** 팀 UI/라우터/데이터 조회·기존 API의 동작을 존중하며, 원본 브랜치는 구현/검증 참고로 보존한다. 이번 대화의 “승인했다”는 바로 앞 GitHub 인증 창에 대한 응답이며 아직 제시하지 않은 이식 실시계획 전체의 승인으로 확대하지 않는다.

후속 사용자 의견 **“최대한 frontend의 개조는 최소화하지만 편의성이 높은 단추가 팝업정도는 가능”**을 반영한다. 기존 외형을 기본으로 유지하면서 명시 선택 버튼과 실제 모호한 출발지의 후보 팝업에 한정해 작은 HTML/CSS 예외를 계획한다. 전체 화면/내비게이션 재설계나 아래 실시계획의 미리 받은 구현 허락으로 확대하지 않는다.

**실시 승인 원문:** 계획 작성 뒤 사용자가 **“다 되면 계획 저장하고 보여주고 시작해”**, 이어 **“체크리스트를 만들어 하나씩 체크하면서 실행 점검 보완 진행해”**라고 명시했다. 아래 M0~M5의 로컬 기준 준비·엔진/최소 접점·필수 선택/후보 팝업·오프라인 검증·보완·기록을 이 승인 범위로 실시한다. 이전의 GitHub 인증 응답과 구분한다. 원격 dj/develop 강제 교체·PR 병합·배포·새 실제 API 예산은 포함하지 않는다.

## 3. 두 브랜치에 남길 문서와 전환 순서

두 브랜치에서 **동일한 상대 경로**로 다음 두 문서를 읽을 수 있게 한다.

1. `docs/development/agent-implementation-spec.md`: 소스 에이전트의 제품 의도·3축·계약·실제 기능·검증·한계. 대상에서는 ‘이미 이식 완료’라는 뜻으로 바꾸지 않는다.
2. `docs/development/agent-engine-migration-plan.md`: 이 계획과 단계 체크표·파일/검증/복구·승인 범위. 대상 착수 후만 실제 진행/성적을 갱신한다.

현재는 `dj/agent` 작업폴더에 두 문서를 작성했다. 최신 사용자 요청에 따른 원본 명세/계획·이슈/PR 기록 게시를 마친 뒤 소스 작업폴더를 깨끗하게 만든다. **명시적 실시 허락을 받은 아래 순서**로 대상 준비를 진행한다.

- 원격 develop SHA 재확인/필요 fetch. `main`·로컬 `develop`을 바꾸거나 병합하지 않는다.
- 이전 로컬 `dj/develop` 이름은 충돌 없는 날짜 포함 보존 이름으로 옮겨 tip을 남긴다. 이전 코드를 새 작업의 출발점으로 사용하지 않는다. 원격의 이전 브랜치는 이 단계에서 변경하지 않는다.
- 최신 `origin/develop`에서 새 로컬 `dj/develop`을 만든다. 시작 직후 HEAD·tree가 기준 SHA와 같은지 확인한다. 과거 개인 브랜치와 merge/cherry-pick하지 않는다. 대상의 upstream을 `develop`로 지정하지 않아 우발적인 develop push를 피하고, 향후 게시 ref는 명시적으로 정한다.
- 두 문서의 게시본을 그대로 복사하고 문서 외 제품 차이0을 확인한다. 대상 상태 문서에는 소스 성적과 대상 미실시를 분리한다.
- 대상의 기준선 검사를 먼저 실행하고, 그 뒤 아래 단계별 최소 이식을 시작한다.

원격 `dj/develop`은 이전 tip을 가리키므로 새 기준 브랜치를 나중에 같은 이름으로 게시할 때 non-fast-forward가 될 수 있다. **이번 계획은 원격 force push/브랜치 삭제를 승인하지 않는다.** 개발 후 원격 보존·게시 방법을 따로 결정하며, 조용히 force 또는 unrelated merge로 맞추지 않는다.

현재 테스트 서버는 작업폴더를 직접 읽는다. 실제 checkout 전에는 소유 PID/명령을 확인해 현재 테스트 서버를 정리하거나 사용자 시험 종료를 확인한다. 예전 백엔드 메모리와 새 프론트 파일을 섞어 테스트하지 않는다. 대상 서버는 명시한 새 포트/세션으로 시작하고 주소를 다시 안내한다. 현재는 서버를 멈추지 않는다.

## 8. 검증 방법과 사실 구분

소스의 backend253/표적59/HTTP19/navigation9/legacy17·15/실HTTP는 **dj/agent의 검증 성적**이다. 대상에 테스트를 복사했다고 대상 성적으로 바꾸지 않는다. 새 기준의 기존 실패도 먼저 실행해 관측하며, 소스에 남은 docstring7건을 대상의 baseline이라고 추측하지 않는다.

1. 대상 baseline: backend unittest, utils 하네스, 기존 API 오프라인 검사를 실행해 SHA·출력·기존 실패를 보존한다. 하네스 `--tests`는 utils/tests이며 backend/DOM 검사를 대신하지 않는다.
2. 의미/진행: 공연→잔잔함→출발지, 설명/불만/부분 정정, 다른 목적 전환, 정상 빈 의미와 깨진 schema의 구분을 독립 기대값으로 검사한다.
3. 탐색: 부대시설+공원 혼합/소수/0건, 출처 ID/좌표, 무료/예산/제외, 미확인 근거를 실제 코드+고정 원본으로 검증한다.
4. 상태: lease/CAS·TTL·캐시밖중복·늦은 응답·다른 탭/대화·새로고침 복원에서 사용자 주장/verified 사실을 구분한다.
5. 선택: 두 번째 묶음의3번≠전체풀3번 fixture, 카드/상세/번호 동일ID, 원점/조건/맥락 불변, 추가 모델/조회0, 과거batch·조건변경 선택 차단.
6. 기존 UI: 지도/전화/저장/날씨·체험 시작/종료 유지, 상세→지도→대화 복귀의 미전송 입력/읽던 위치/음성 자동시작0, 보호 해시/파일 diff 확인. HTML/CSS 예외는 선택 버튼/모호한 출발지 dialog에 필요한 행만 설명하고 popup 취소/선택 뒤 포커스·대화 보존을 검사한다.
7. 실모델/실원천은 위 P0 이후 별도 예산 승인으로 평가한다. 소스 B34/60·C25/30·조회12/12를 이식 후 성적으로 재사용하거나 예산을 자동 초기화하지 않는다. 실제 마이크/GPS/시각/사용성은 사용자 QA다.

검사 스크립트의 실제 계약을 먼저 확인한다. 구형 `check_chat_ui.cjs`는 기본 실제 Naito 호출과5174/구형 selector를 전제할 수 있으므로 그대로 실행하지 않는다. 개발자 `/checks` 검사를 사용자 UI 검사로 집계하지 않는다. 새 adapter에 맞는 격리 fixture와 실제 HTTP/DOM 계약을 먼저 고정한다.

## 9. 제외·미정·복구

이번 최소 엔진 이식에서 ♡찜·일정 달력/회차·새 영화 API·검색 반경/페이지 확대·새 저장 정책·전체 내비게이션·아이콘/날씨·인증/DB·RAG/KONNECT 전체 이식은 제외한다. 검증된 추천 이유1~2개·0건 원인별 대안·한 단계 취소는 후속 검토 안건이다.

기준 prepare 단계와 엔진 단계마다 허용 파일·바이트/해시·diff를 보존한다. P0 실패 또는 보호 파일 차이가 생기면 해당 단계 추가 작업을 멈추고 원인을 확인한다. 이전 단계의 이식분만 복구하며 사용자 저장 자료와 소스 브랜치를 삭제하지 않는다. `reset --hard`, 강제 push, main/develop 병합으로 맞추지 않는다. 현재 Git 인증은 계정 선택을 명시해 해결했고 원본 코드 push를 확인했다. 이후 인증 실패가 재발하면 토큰을 대화/문서에 요청하거나 기록하지 않는다.

원격 branch 재구성/게시, 새 PR, 병합·배포, 실유료 호출은 별도 범위를 확인한다. 승인 범위의 현재 다음 행동은 **사용자 로컬 실기기 QA**다. 단계마다 실행·점검·보완·체크 결과를 기록했으며 실제 기기·실모델 평가까지 완료한 것으로 표시하지 않는다.
