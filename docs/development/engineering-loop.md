# 개발 도구·반복 검증·컨텍스트 운영

이 문서는 김동조 개인 작업 절차다. 팀 공통 합의를 새로 확정하지 않으며 [TEAM_WORKFLOW.md](../../TEAM_WORKFLOW.md)를 우선한다.

## 구현 전 승인 절차 — 필수

2026-11-01 사용자는 “절대 승인없이 니 맘대로 안한다”, “조사 계획 실시계획 보완 허락 등으로 해야한다고 적어놓고 기록해”, “front end는 건드리지마 내 담당이 아니다”라고 명시했다. 기존 계획·담당 확인 규칙을 실제로 따르지 않고 개선 의견을 구현 승인으로 해석한 잘못을 되풀이하지 않는다. 이번 지시는 절차를 기록하라는 허락이며 서비스 구현 허락이 아니다.

| 단계 | 제출할 내용 | 다음 단계 조건 |
|---|---|---|
| 1. 조사·원인 분석 | 현재 상태, 재현 근거, 확인 사실과 추측, 담당 영역 | 조사 결과를 근거로 계획 작성. 코드 변경 없음 |
| 2. 개발계획 | 목표, 선택지, 변경 필요성, 영향 범위, 담당/제외 범위 | 계획 검토에 필요한 내용 정리 |
| 3. 실시계획 | 대상 파일, 단계별 체크표, API/타 담당 영향, 검증·복구 방법 | 사용자가 승인할 구체적인 범위 제시 |
| 4. 검토·보완 | 사용자 피드백 반영, 남은 미정, 계획 버전 | 보완된 계획으로 명시적 허락 요청 |
| 5. 명시적 허락 | 허락 원문/시점, 승인한 계획·파일·범위, 제외 사항 | 정확히 승인된 범위만 실시 가능 |
| 6. 실시·검증 | 최소 변경, 실행 전후 상태, 실제 검증·실패·미실시 | 범위 변경은 중지하고 새 허락. 결과 보고 |

- 개선 제안·샘플 대화·질문·자유 형식 피드백은 구현 동의로 추정하지 않는다. 읽기 전용/수정 금지 상태는 명시적으로 해제되기 전까지 유지한다. 답변 대기나 시간 경과도 승인이 아니다.
- 작업별 `plan_dj/` 체크표에 현재 단계, 계획 버전, 허용/금지 파일·행동, 승인 근거를 적는다. `state.json`에는 현재 구현 승인 유무와 다음 허용 행동을 명시한다. 승인 근거가 없으면 “미승인”이다.
- 프론트는 담당 밖으로 수정 금지다. UI가 다른 폴더에 있거나 사본·패치라는 이유로 수정하지 않는다. 담당자 전달용 원인·제안 문서만 작성한다. `dj/develop`은 작업 위치이며 타 담당 수정 권한을 주지 않는다.
- `main`·`develop`·병합·push·배포는 별도 명시 승인 사항이다. 완료 작업의 커밋 상시 요청은 서비스 구현 또는 범위 변경 허락으로 확대하지 않는다.
- 명시적으로 승인된 같은 범위 안에서는 불필요하게 재확인하지 않는다. 범위·담당·계약이 바뀌면 새 허락을 받는다.

개인 체크표에 사용할 최소 기록:

```text
현재 단계: 조사 / 계획 / 실시계획 / 보완 / 허락 대기 / 승인 범위 실시
계획 버전·위치:
허용 파일·행동:
금지 파일·행동:
실시 승인: 미승인 / 승인
허락 근거: 사용자 원문·시점·대상 범위 (미응답이면 없음)
검증·복구 방법:
다음 허용 행동:
```

## 하네스: 기억에 의존하지 않고 실행해서 확인

`python utils/scripts/harness.py --tests`는 Python 문법·docstring, 활성 문서의 상대 링크, 생성 색인·현재 상태의 최신성, 개발 도구 테스트를 한 번 실행한다. 실제 서비스가 생기면 해당 기능의 빌드·단위·API·브라우저 검증을 별도 추가한다. 검증 명령·실패 원인·미실시 항목을 남긴다. 완료와 PASS를 자동 추정하지 않는다.

경로·실패·종료 조건이 중요한 개발 도구는 임시 저장소·파일로 테스트한다. 단순 문구 변경마다 구현을 복제하는 테스트는 추가하지 않는다. 사용자 파일을 되돌리는 자동 repair, 무제한 재시도, 자동 결제·배포·push는 구성하지 않는다.

**실제 검사 범위와 한계:** `harness.py`는 코드/문서/색인 검증, `loop.py`는 목표·범위·반복 횟수 기록, `commit_report.py`는 브랜치·마감·보고문·선택 경로 검사다. 이 도구들은 사용자 메시지의 승인 여부를 판정하거나 승인 없는 파일 쓰기를 차단하지 않는다. 현재 구현에 그런 차단 장치가 있다고 보고하지 않는다. 별도 승인 차단 도구 추가는 계획·허락을 거쳐야 하며 이번에는 도구 코드를 바꾸지 않는다.

## 루프: 작은 가설과 증거로 다음 행동을 결정

1. 위 승인 절차의 허락 근거와 범위를 확인한다. 목표·허용 파일·완료 기준·담당 영역을 정하고 관련 함수·스키마만 찾아 읽는다. 미승인 상태에서는 코드 수정 루프를 시작하지 않는다.
2. 실패에 관한 가설 하나를 세우고 최소 변경을 한다.
3. 필요한 검증을 실행하고 실제 결과를 기록한다.
4. 통과하면 다음 통합 단계로 이동한다. 실패면 새 증거가 있는 수정만 시도한다.
5. 기본 3회 후에도 미해결이거나 승인/정보가 필요하면 현재 상태·가설·다음 행동을 남겨 확인한다. 한도에 도달했다고 완료 처리하지 않는다.

```powershell
python utils/scripts/loop.py start docs/development/loops/example.json --goal "구체 목표" --scope utils --limit 3
python utils/scripts/loop.py record docs/development/loops/example.json --outcome fail --hypothesis "가설" --change "작은 변경" --evidence "실행 명령과 실제 오류"
python utils/scripts/loop.py status docs/development/loops/example.json
```

이는 기록 도구이며 자동 코딩 에이전트가 아니다. pass·blocked·exhausted 뒤에는 동일 기록을 무단 재시작하지 않는다. 기록에는 실제 키·사용자 위치 원문을 넣지 않는다.

## 대화가 길어져도 상태를 잃지 않기

| 계층 | 파일 | 읽는 시점 |
|---|---|---|
| 공통 규칙 | 루트 TEAM_WORKFLOW.md·AGENTS.md | 작업 시작 |
| 짧은 현재 상태 | current-state.md, 편집 원본 state.json | 작업 시작·대화 압축·인계 |
| 파일/기능/함수/구조 | repo_index.md·repo_reverse_index.md·repo_tree.md | 작업 위치 탐색 |
| 작업 목록 | tasks.md | 우선순위·선행조건 확인 |
| 상세 경위 | discussion-log.md·기술검토 문서 | 결정 이유·충돌 확인에 필요한 부분만 |
| 완료 보고문 원문 | reports/ | 사용자 출력·커밋 메시지 확인 |

사용자 정정·범위 변경은 즉시 state와 상세 이력에 반영한다. state는 사용자/브랜치, 현재 목표, 승인 범위, 완료·검증, 진행, 다음 행동, 미정, 필요한 문서의 8개 목록으로 유지한다. 목록당 최대 10개·전체 최대 6500자로 제한하되 중요한 결정을 잘라 버리지 말고 상세 파일에 옮겨 연결한다. 문자 수는 실제 모델 토큰 수가 아니다.

감시기는 변경된 state를 렌더링하고 파일 색인을 갱신한다. **이 채팅 원문을 플랫폼에서 자동 수집하거나 의미를 자동 압축하는 기능은 없다.** AI가 매 작업 중 의미 있는 요구·결정·검증·미정과 다음 행동을 기록한다. 모든 과거 대화를 다시 읽었다고 주장하지 않는다.

## 토큰과 재작업을 줄이는 방법

- `catalog.py --find 키워드` 또는 `rg -n`으로 경로·함수를 좁히고 필요한 줄만 읽는다. 전체 트리·로그·PRD 반복 출력은 피한다.
- 해시가 바뀐 파일만 재검토하되, 요구사항이나 외부 API 정책이 바뀌면 이전 요약을 신뢰하지 말고 근거를 다시 확인한다.
- 규칙은 TEAM_WORKFLOW에, 폴더별 차이는 해당 AGENTS에 둔다. 같은 규칙·서비스 코드·긴 설명을 여러 군데 복제하지 않는다.
- 결과 로그는 실제 오류·최종 수치를 중심으로 제한하되 완료 보고문 전체는 보존한다. 민감값·전체 API 응답을 무조건 출력하지 않는다.
- 기능→파일 분류를 갱신하고, 재사용 코드는 utils에서 찾는다. 과거 브랜치 파일을 통째로 다시 읽거나 미치환 템플릿을 반복 생성하지 않는다.
- 자동 색인·오프라인 하네스가 서비스의 실제 작동을 입증한 것처럼 보고하지 않는다. 검증이 충분하면 같은 검사를 이유 없이 반복하지 않는다.

## 완료·커밋

state/상세 이력/작업 목록 → 감시 또는 일회 갱신 → 관련 검증 → 완료 보고문 파일 → 명시 경로 커밋 → 메시지 바이트 일치 확인 → 같은 보고문 출력 순으로 진행한다. 전체 보고문을 요약·재작성하지 않는다. 자동 감시기는 커밋하지 않는다. **커밋할 때마다 변경 내용·검증 결과를 사용자에게 보고한다.** push는 별도 요청 때만 하며 제출 마감 이후에는 커밋하지 않는다.

```powershell
python utils/scripts/commit_report.py --report docs/development/reports/보고문.md --path utils
# 위 명령은 사전검사만 한다. 승인된 작업을 실제 커밋하려면 --commit을 명시한다.
```

기존 staged 변경이 있으면 자동으로 섞지 않고 중단한다. 기존 사용자 명의·정확한 브랜치·마감·LF UTF-8 보고문을 확인한다. 이 도구는 Git 쓰기 권한을 우회하지 않으며 세션의 권한 절차를 그대로 따른다.
